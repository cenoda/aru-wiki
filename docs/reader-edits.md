# 독자가 쓰는 글 (로그인 없이)

2026-11-12 사용자 결정: 독자가 문단을 고치고, 글을 보태고, 새 문서를 쓸 수 있게 한다. 안전한 방식으로 시작한다. **보낸 글은 쓴 사람의 브라우저에서만 바로 보이고, 운영자가 승인한 뒤에야 다른 사람에게 보인다.** 문제가 없으면 나중에 작은 수정부터 바로 공개하는 방식으로 풀 수 있다(아직 정하지 않음).

기계가 쓰는 문서(`scripts/theme/`, `data/generated/`)는 건드리지 않는다. 독자의 글은 `data/manual/reader-edits.json`에 따로 쌓이고 화면에서 겹쳐 보인다.

## 독자가 할 수 있는 것

| 무엇 | 어디서 | 붙는 자리 |
|---|---|---|
| 문단 고치기 | 문단 끝의 ✎ | 그 본문 버전의 그 문단(글이 글자 그대로 같을 때) |
| 글 보태기 | 절 끝의 `＋ 이 절에 글 보태기` | 그 제목의 절 끝. 절이 없어지면 문서 끝 「독자가 쓴 글」 |
| 새 문서 | 검색에서 없는 이름 → `「이름」 문서 쓰기`, 또는 `/wiki/이름` | `/wiki/이름` (3D 지도에는 나오지 않고 검색으로 찾는다) |

- 글 1,500자까지. 근거와 닉네임은 선택. 체크 두 개(직접 쓴 글, CC BY-SA 4.0 동의)가 있어야 보낼 수 있다.
- 쓴 사람이 보던 버전(`v`)보다 앞 버전을 고른 독자에게는 보이지 않는다(스포일러).
- 실린 글에는 `독자 수정`·`독자 작성` 표시, 기다리는 글에는 `검토 중 · 나만 보임` 표시가 붙는다.
- 결과는 서버에 묻지 않는다. 배포된 `reader-edits.json`에 그 제안의 id가 있으면 실린 것이고, `rejected`에 있으면 「내가 보낸 제안」에 사유와 함께 나온다.

## 운영자가 하는 일

```
node scripts/suggest/review.mjs pull            # 서버 대기열 받기
node scripts/suggest/review.mjs list            # 아직 정하지 않은 제안
node scripts/suggest/review.mjs show <id>       # 원문과 고친 글, 살펴볼 점
node scripts/suggest/review.mjs approve <id>    # 싣기 (--v 5.0 으로 공개 버전을 늦출 수 있다)
node scripts/suggest/review.mjs reject <id> --note "사유"
node scripts/suggest/review.mjs remove <id> --note "사유"   # 실었던 글 내리기
node scripts/suggest/review.mjs stale           # 문서가 다시 쓰여 붙을 자리를 잃은 고침
```

승인·거절은 `data/manual/reader-edits.json`에 적힌다(승인 시각 `approved_at`은 「최근 바뀜」 페이지에 쓰인다. 그 전에 실린 글은 날짜만 있다). 커밋하고 배포해야 사이트에 나온다. `show`의 "살펴볼 점"은 나무위키 문법 흔적, 빠른 붙여넣기, 긴 글, 주소, 유출 언급 같은 것을 알려 주는 표시일 뿐이고 통과 판정이 아니다. LLM 검사(근거 대조, 스포일러)는 아직 없다. 본문 파이프라인의 LLM 호출 코드가 바뀌는 중이라 겹치지 않게 뺐다.

승인 전에 볼 것: 다른 사이트 문장을 옮긴 글이 아닌가(긴 글은 특이한 문장을 따옴표로 검색), 고른 버전보다 뒤의 내용이 없는가, 유출이 아닌가, 실제 사람을 헐뜯지 않는가.

## 받는 쪽

- `scripts/suggest/server.mjs`: `POST /api/suggest`. `scripts/report-server.mjs`가 `/api/report`와 함께 받는다. 주소(IP)는 디스크에 쓰지 않고, 매일 바뀌는 값과 함께 해시해 메모리에서 횟수만 센다(한 주소 1시간 5번, 전체 하루 200번).
- 대기열: `REPORT_FILE` 옆의 `suggestions.jsonl`(서버에서는 `/var/lib/aru-report/suggestions.jsonl`).
- 숨긴 입력란을 채운 봇에게는 "받았다"고만 답하고 저장하지 않는다.

### 서버에 올릴 때 (아직 하지 않음)

화면만 먼저 배포하면 ✎를 눌러 보내도 "서버에 연결할 수 없습니다"가 나온다. 순서:

1. `/opt/aru-report`에 `report-server.mjs`와 `suggest/server.mjs`, `suggest/shared.mjs`를 올리고 `aru-report.service`를 다시 시작한다.
2. Caddyfile의 `aru.wiki` 블록에서 `/api/suggest`도 `127.0.0.1:8787`로 넘긴다.
3. 사이트를 배포한다.

## 저작권법 확인 (2026-11-12, 법제처 국가법령정보센터, 법률 제21595호·시행 2026-10-29)

독자의 글을 싣는 순간 운영자는 저작권법 제2조 제30호 나목("이용자들이 … 정보통신망을 통하여 저작물등을 복제ㆍ전송할 수 있도록 서비스를 제공하거나 그를 위한 설비를 제공 또는 운영하는 자")의 온라인서비스제공자에 해당할 수 있다.

- **제102조 제1항 제3호(저장 서비스의 책임 제한)** 는 가목에서 "제1호 각 목의 요건을 모두 갖춘 경우"를 요구하고, 제1호 나목은 "온라인서비스제공자가 저작물등이나 그 수신자를 선택하지 아니한 경우"다. 운영자가 글을 하나씩 골라 싣는 지금 방식이 이 요건에 맞는지는 조문만으로는 확실하지 않고, 맞지 않는다고 볼 여지가 있다. 제1호 다목(반복 침해자의 계정을 해지하는 방침)도 계정이 없는 사이트에 어떻게 적용되는지 확인하지 못했다. **즉 "이용자가 올린 글이라 몰랐다"는 보호를 기대하지 않고, 승인할 때 직접 확인하는 것을 전제로 운영한다.**
- **제102조 제3항**: 침해가 일어나는지 모니터링하거나 적극적으로 조사할 의무는 없다(제1항의 책임 제한과 관련해서).
- **제103조**: 권리를 주장하는 사람이 소명해서 중단을 요구하면 즉시 내리고 그 사람에게 알린다(제2항). 요구를 받을 사람(수령인)을 정해 쉽게 알 수 있게 공지해야 한다(제4항). 공지하고 요구에 따라 내리면 책임이 면제되지만, 침해를 안 때부터 요구를 받기 전까지의 책임에는 적용되지 않는다(제5항).

그래서 한 것:

- 문서의 「출처와 라이선스」에 받는 곳(contact@aru.wiki)을 적었다(제103조 제4항).
- 내리기: `review.mjs remove <id>` → 커밋 → 배포. design.md의 72시간 답변 규칙과 별개로, 요구가 소명되면 바로 내린다.
- 제103조 제2항은 글을 쓴 사람에게도 알리라고 한다. 쓴 사람의 연락처가 없으므로 알릴 방법이 없다. `rejected`의 사유는 실리기 전의 제안에만 쓴 사람 브라우저에 보인다.

확인하지 못한 것: 판례와 시행령(제103조 제7항의 소명·공지 방식), 정보통신망법의 임시조치 조항. 법률 자문이 아니다.
