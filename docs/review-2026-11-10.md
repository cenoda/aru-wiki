막 밖 임무(시리즈·이벤트)를 갈래 보기에 붙인 뒤(`a9c7b94`) 사용자와 나눈 점검 내용이다. 사용자가 정한 것과 제안 중인 것을 나눠 적는다. 정해진 항목은 design.md에도 반영해야 한다(아래 "design.md 반영할 곳").

1단계 후반이다. 2단계 본 작업(로어 테마 노드, 버전 스냅샷, 슬라이드 카드, 신뢰도 등급, 3D)은 시작하지 않았다.

| 1단계 항목 | 상태 |
|---|---|
| 임무 데이터와 필수 선행 (정보 상자 파싱) | 완료. 막 238개, 막 밖 임무 1,451개를 묶음 726개로 정리 |
| 한국어 공식 명칭 | 완료 |

용어: 문서와 코드의 "엣지"는 카드 두 개를 잇는 선 하나다. 보고할 때는 "연결선"이라고 쓴다.

## 2. 운영 방침

### 2.1 진행도 체크: 만들지 않는다 (결정)

- 설계는 브라우저 저장(localStorage)이라 로그인과 서버는 필요 없다. 그래도 기기 사이에 공유되지 않고, 브라우저 데이터를 지우면 사라져 사용자가 기대하는 "내 진행도"가 되지 못한다.
- 스포일러 차단은 버전 선택("7.2까지 공개")이 이미 맡는다.
- Gscouter도 같은 이유로 만들지 않았다.

### 2.2 오류 신고: 카드마다 GitHub 이슈 링크를 두지 않는다 (방향 합의, 형태 미정)

- 사용자 제기:
  - GitHub 이슈는 일반 방문자에게 맞지 않는다.
  - 위키백과식 운영이 낫지 않나?
  - 카드마다 둘 만큼 정확도가 낮은가?
- 위키백과식 공개 편집은 계정, 편집 이력, 되돌리기, 반달 대응, 서버 DB가 필요하다. design.md의 "보류: 계정, 서버 DB"와 맞지 않는다. 자동 생성 문장은 인용과 출처(리비전)에 묶여 있어서 직접 고치면 그 연결이 끊기는 문제도 있다.
- 제안:
  - 신고 창구는 연결선 정보 카드 아래 링크 하나만 둔다. 예: "틀린 곳 알려 주기" → contact@aru.wiki
  - 신고 장치보다 정확도 측정이 먼저다. 지금 오류율은 아무도 모른다. 권장 연결선 20~30개를 표본으로 사람이 읽어 오류율을 잰다(design.md 5절 5번).

### 2.3 배포: OCI 인스턴스 (결정)

필요할 때 사용자에게 인스턴스를 요청한다. 사이트는 `npm run build` 결과물(정적 파일)뿐이라 무료 등급 ARM 인스턴스로 충분하다. 사용자에게 받을 것:

- SSH 접속 정보
- 80·443 포트 개방 (OCI Security List와 인스턴스 방화벽 둘 다)
- aru.wiki DNS A 레코드를 인스턴스 IP로

웹 서버는 Caddy를 제안한다(인증서 자동 갱신).

## 3. UI 개선 (새 에이전트에게 맡김)

### 3.1 카드 끌기: 막는다

- 지금은 React Flow 기본값 때문에 카드를 끌 수 있다. 관성, 가속, 복원력이 없어 모양이 그대로 꼬인다. 사용자 평: "아예 안 움직이는 게 나을 수준".
- 제안: `<ReactFlow nodesDraggable={false}>`로 막는다.
  - 지도는 ELK가 정한 배치를 보여 주는 화면이라 물리 시뮬레이션과 맞지 않는다.
  - 막으면 `RouteEdge`의 "끌어서 어긋나면 smoothstep으로 대체" 분기는 지워도 된다(`src/FocusView.tsx`).
- 끌기에 관성과 복원력을 넣는 쪽을 고른다면 그 판단은 새 에이전트에게 맡긴다.

### 3.2 화면 이동 범위에 복원력

- 지금은 화면 중심을 거의 끝없이 바깥으로 옮길 수 있다.
- 딱딱한 벽: React Flow `translateExtent`에 그래프 범위와 여백을 준다.
- 탄성 복원(사용자 제안): 이동이 끝날 때(`onMoveEnd`) 범위 밖이면 애니메이션으로 되돌린다.
- 아틀라스와 갈래 보기는 범위가 다르니 각각 계산한다.

### 3.3 빈 공간

- 원인: 아틀라스가 지하철 노선도 배치(시대별 줄, 버전별 열, 같은 이야기는 한 높이)라서 다음 부분이 길게 빈다. 짧은 노선의 오른쪽, 막이 적은 버전 열, 시대 사이 간격(`ERA_GAP` 90)이다.
- 검토한 방향:
  - (가) 버전 열 폭을 내용에 맞추고, 짧은 노선끼리 한 줄에 더 채운다.
  - (나) 빈 곳에 그 버전의 지역·주요 사건 같은 정보를 놓는다.
  - (다) 지역 단위로 묶어 배치를 새로 짠다.
- **사용자 선택: (나), 그리고 임무 카드에 이미지를 넣는다** (3.4).
- 디자인 판단이 크므로 새 에이전트가 화면 시안 두세 개를 먼저 보여 준다.

### 3.4 임무 이미지 (사용자 제안, 출처 미정)

임무 카드나 빈 공간에 대표 이미지를 둔다.

- 전설 임무: 그 전설 임무의 캐릭터
- 마신 임무 중간장: 데인슬레이프처럼 그 장의 중심 인물
- 그 밖에는 적당히 고른다.

**저작권과 출처.** design.md는 "이미지는 가져오지 않는다"(3절)와 "추출 자료 금지"(원칙 1)를 정해 두었다. 후보별로 보면:

| 후보 | 판단 |
|---|---|
| Enka.Network 아이콘 (Gscouter 방식) | **쓰지 않는다.** Gscouter는 `enka.network/ui/<icon>.png`를 불러오고 비영리 팬 프로젝트임을 밝힌다. 그러나 이 아이콘은 게임 클라이언트에서 추출한 에셋이라 aru-wiki 원칙 1에 걸린다 |
| Fandom 이미지 파일 | 쓰지 않는다. 대부분 HoYoverse 소유이고 상당수가 추출본이다. design.md 3절도 금지한다 |
| 공식 홍보 이미지 (공식 홈페이지 캐릭터 소개, 공식 SNS 공개 일러스트) | 추출본은 아니다. 다만 HoYoverse 소유이고, 웹사이트에서 쓰는 것을 허용하는 공식 규정 원문을 아직 찾지 못했다. 찾은 것은 2021년 팬 굿즈 가이드 보도뿐인데, 굿즈 이야기이고 공식 소재의 직접 사용·부분 수정을 제한한다. 쓰려면 현행 규정을 확인하거나 HoYoverse에 문의한다 |
| 직접 그린 그림 (실루엣, 지역 문장, 상징 아이콘) | 저작권 문제가 없다. Gscouter도 원소 아이콘은 직접 그렸다. 캐릭터 얼굴 대신 상징물로 표현한다 |

- **제안:** 직접 그린 상징 아이콘으로 시작한다. 공식 홍보 이미지는 규정을 확인한 뒤 추가한다.
- **확인할 것:**
  - 이미지는 서버에 복사하지 않고 출처 링크로 불러오는가?
  - 출처 표기는 어떻게 하는가? 예: "© HoYoverse"
  - HoYoverse가 요청하면 즉시 삭제하는가? (원칙 4)
- **임무와 인물 짝짓기:**
  - 재료: `data/generated/quest-characters.json`(임무별 등장인물 2,231건)
  - "중심 인물" 하나를 고르는 규칙은 새로 정해야 한다. 등장 횟수만으로는 페이몬과 여행자가 뽑힌다.
- **스포일러:**
  - 인물의 얼굴이나 정체가 곧 스포일러인 경우가 있다. 이미지도 버전 선택기를 따른다.
  - 정체가 늦게 드러나는 인물은 공개 버전 이후에만 보인다.
